\begin{abstract}
Microservice REST APIs expose cross-service workflows that no single OpenAPI specification describes, and the dominant ``HTTP 2xx is a pass'' oracle accepts soft errors that downstream services have already flagged. \textbf{MIST} (Microservice Integration \& Scenario Tester) turns OpenTelemetry/Jaeger traces and OpenAPI specs into runnable workflow tests for such systems. Three design choices distinguish it from prior REST API testers. A \emph{Sniper Mutator} picks one parameter and one fault category per negative variant, so each downstream anomaly is attributable to a specific mutation. A \emph{Root API Mode} drives only gateway-entry calls and reads internal behaviour off the trace, sidestepping state fabrication on internal endpoints. A \emph{Trace-Aware Oracle} replaces the status-class check with span causality, error-status propagation, response-body soft-error rules, and root-cause matching. MIST ships with a TrainTicket~\cite{Zhou2021TrainTicket} case study, a 10-fault injected-fault corpus, and a public deployment; the bundled demo runs from one properties file. Source: \url{https://github.com/miaoti/Rest/}. Screencast: \url{https://TODO-screencast.example.invalid}.
\end{abstract}

\section{Introduction}\label{sec:intro}

Microservice systems exchange business state across deeply coupled REST endpoints, and validating that state from outside the system is now the bottleneck for black-box test generation. Two gaps in current REST testing tools \cite{Arcuri2019EvoMasterTOSEM,MartinLopez2021RESTest,Atlidakis2019RESTler,Liu2022MoRest,Corradini2024DeepREST,Stennett2025AutoRestTest} are particularly painful in this setting.

\emph{Weak oracles.} The de facto oracle---the response status class---accepts any 2xx response, even when the body carries a soft-error envelope (\texttt{status:0, msg:...}) that a downstream service has already produced to flag a rejection. Such soft errors accumulate in test reports unflagged.

\emph{State fabrication on internal endpoints.} Driving every API directly requires fabricating consistent state across many services. Generators that fall back to random UUIDs exercise rejection paths instead of business logic.

MIST closes both gaps with three design choices. The Sniper Mutator targets exactly one parameter on exactly one root API per negative variant, so any downstream anomaly traces back to a known mutation. Root API Mode drives only gateway-entry calls and reads internal behaviour off the captured Jaeger trace, so MIST never has to fabricate internal state. The Trace-Aware Oracle replaces the lone status-class check with four assertion families derived from the trace and the response body. The artifact is open source at \url{https://github.com/miaoti/Rest/}, includes a TrainTicket~\cite{Zhou2021TrainTicket} case study with a 10-fault injected-fault corpus, and runs from a single properties file.

\section{Background and Motivating Example}\label{sec:bg}

Consider \texttt{POST /api/v1/adminroute\-service/admin\-route} on TrainTicket, which creates a route from a \texttt{startStation}, an \texttt{endStation}, and a \texttt{stationList}. On a negative variant whose end station is absent from the station list, the service answers \emph{HTTP 200} with a soft-error envelope---\texttt{status:0}, \texttt{data:null}, and an explanatory \texttt{msg} field (Figure~\ref{fig:trace} renders the full body).

A status-class oracle records this as a pass: every span in the captured Jaeger trace returns 200, and no span sets an OpenTelemetry error status anywhere in the tree---every network-level signal confirms a clean 200. The only failure evidence is the envelope itself. A trace-aware oracle with a per-API body-pattern rule catches it and pins the rejection to \texttt{ts-admin-route-service}.

\section{Tool Overview and Architecture}\label{sec:arch}

\begin{figure*}[t]
  \centering
  \input{figures/architecture.tex}
  \caption{MIST architecture. The Spec Ingestor (i) reads an OpenAPI specification; the Sequence Generator (iii) consumes Jaeger traces to mine workflow scenarios; the Sniper Mutator (iv) consumes the run's \texttt{.properties} configuration. The dotted box is the System Under Test. Solid arrows are HTTP requests issued by MIST; the dashed arrow is the Jaeger trace pulled back per step by the Trace-Aware Oracle.}
  \label{fig:arch}
\end{figure*}

Figure~\ref{fig:arch} shows the five components.

\textbf{(i) Spec Ingestor.} Parses an OpenAPI specification---obtained from the SUT operator or aggregated from per-service \texttt{/v3/api-docs} endpoints---and emits a multi-service test configuration. The bundled TrainTicket spec contains 265 operations across 37 REST-exposed services, which defines MIST's test scope. Components without a discoverable HTTP surface (async workers, message brokers, internal-only RPC) lie outside any black-box tool's reach by construction.

\textbf{(ii) Semantic Dependency Registry.} A producer/consumer index over the spec. For every parameter whose name ends in \texttt{Id}/\texttt{ID}/\texttt{uuid}, it records the API and JSON path that historically produces a matching value. At generation time the registry returns a binding that the Sequence Generator wires just-in-time, so a value computed at runtime by an earlier step plugs into the right field of a later step.

\textbf{(iii) Sequence Generator.} Mines workflow scenarios from Jaeger traces through a five-phase pipeline: cross-trace data-dependency merging, session/time-window merging, single-root deduplication, weakly-connected-component shattering on the dependency graph, and missing-baseline decomposition. Under Root API Mode (\texttt{mst.gener\-ate.only.first.step=true}, the default; Section~\ref{sec:rootmode}) the generator keeps every gateway-entry call in a scenario and prunes internal step-API spans. A scenario with three root calls becomes a 3-step JUnit test.

\textbf{(iv) Sniper Mutator.} Builds an invalid-input pool per parameter from eight schema-aware fault categories (TYPE\_MISMATCH, REGEX\_MISMATCH, SEMANTIC\_MISMATCH, OVERFLOW, EMPTY, NULL, SPECIAL\_CHARACTERS, BOUNDARY\_VIOLATION). For each negative variant it locks one parameter, one fault category, and one fault value at one root call (Section~\ref{sec:sniper}).

\textbf{(v) Trace-Aware Oracle.} After each request, it fetches the corresponding Jaeger trace and evaluates four assertion families: HTTP status class, response-body soft-error pattern (LLM-inferred, cached per API), span error-status propagation, and root-cause matching against the injected-fault registry.

\section{Design}\label{sec:design}

\begin{figure*}[t]
  \centering
  \input{figures/trace_oracle.tex}
  \caption{Captured Jaeger trace from a Sniper negative variant against \texttt{POST /api/v1/admin\-route\-service/admin\-route} on TrainTicket (trace ID \texttt{d4c577d4\dots\,acf6}; from this repository's Allure attachments). Every span carries \texttt{http.status\_code=200} and no \texttt{otel.status\_code=ERROR} is set; the Trace-Aware Oracle catches the failure via the cached body-pattern rule and pins the rejection to \texttt{ts-admin-route-service}.}
  \label{fig:trace}
\end{figure*}

The Sniper Mutator's single-fault discipline is what makes the Trace-Aware Oracle's downstream signals causally interpretable, and Root API Mode's external-only driving is what lets the trace stay clean of confounding internal calls. None of the three could close the oracle and state-fabrication gaps alone; the combination is what does.

\subsection{Sniper Mutator}\label{sec:sniper}

A test that mutates several parameters at once leaves the oracle unable to attribute a downstream anomaly to any specific cause; a single-fault test on a non-root call has the dual problem, because the trace prefix is itself driven by other, possibly mutated, values. The Sniper Mutator tightens both axes by picking one parameter and one fault category per variant at the first root call in the scenario (Algorithm~\ref{alg:sniper}).

\begin{algorithm}[H]
\caption{Sniper variant generation.}\label{alg:sniper}
\begin{algorithmic}[1]
\State $r \gets$ first root call in the scenario
\State $p,\, c \gets$ round-robin pick of one parameter on $r$ and one fault category applicable to its schema
\State lock $(r, p, c, v)$ on the variant; fill other parameters from positive sources (shared pool, smart fetch, just-in-time bind)
\State record $(r, p, c, v)$ as the fault target on the test case
\end{algorithmic}
\end{algorithm}

A schema-applicability filter rejects nonsense combinations such as a 5000-character OVERFLOW string on a boolean parameter (which would in fact be a TYPE\_MISMATCH). Round-robin scheduling visits each applicable $(p, c)$ pair before any repeats, so coverage breadth does not depend on randomness. The recorded $(r, p, c, v)$ tuple is the only piece of information the report needs to attribute a failure to its mutation.

\subsection{Root API Mode}\label{sec:rootmode}

Internal microservice endpoints presuppose state that only specific upstream calls can create: an \texttt{orderId} that exists in the database, a session whose token has not expired, a route that has stations. A generator that drives those endpoints directly has to fabricate the state, and a fabrication failure is indistinguishable from a real test failure.

Root API Mode sidesteps that problem. The generator keeps only the gateway-entry HTTP spans of each Jaeger scenario---those with no HTTP parent---and replays them externally; the internal behaviour they trigger is observed through the captured trace, not driven. The writer emits one JUnit step per root call, and a Jaeger fetch attached to each step pulls back the full causal subtree. The mode toggles on a single property (\texttt{mst.gener\-ate.only.first.step}); this paper reports only the default root-only mode.

\subsection{Trace-Aware Oracle}\label{sec:traceoracle}

For the trace in Figure~\ref{fig:trace} the status-class check passes (200 on every span). The Trace-Aware Oracle reaches the right verdict by combining three further signals. \emph{Span causality} checks that the trace tree matches the structural pattern recorded in the original scenario, so a missing internal call surfaces even when every observed call returns 200. \emph{Error-status propagation} fails the test if any descendant span carries \texttt{otel.status\_code=ERROR} or \texttt{http.status\_code}~$\geq 400$. \emph{Soft-error body rules}, learned by a one-shot LLM call and cached per API,\footnote{The cache lives at \texttt{target/soft-error-rule-cache.json}. Each distinct API costs roughly two LLM calls regardless of how many tests touch it, so the validation budget is amortised across the run.} catch envelope patterns such as \texttt{status:0, data:null} on a 2xx response. The oracle also matches the response \texttt{faultName} against the injected-fault registry to attribute a confirmed failure to the recorded $(r, p, c, v)$ mutation.

\section{Usage and Case Study}\label{sec:case}

\subsection{Targeted regression after a change}

A developer modifies the \texttt{ts-admin-route-service} input validation. The relevant scenarios are already mined; a single re-run with \texttt{faulty.ratio=0.8} re-exercises the service with the same Sniper negative variants and surfaces any regression in the fault-detection report:
\begin{lstlisting}[basicstyle=\footnotesize\ttfamily,frame=none,numbers=none]
$ java -jar target/restest.jar \
   src/main/resources/My-Example/trainticket-demo.properties
\end{lstlisting}

\subsection{Exploratory fault detection}

A QA engineer runs the bundled demo end-to-end. The configuration emits and executes 2733 test cases\footnote{Variant count from a representative run on the bundled deployment, fault-detection report \texttt{trainticket\_twostage\_test\_1778039778981}.} on TrainTicket against the 10-fault corpus described in \texttt{INJECTED\_FAULTS.md}. Wall-clock time is roughly 20\,h, of which $\sim$12\,h is LLM inference (DeepSeek \texttt{deepseek-chat}). Almost all LLM cost is positive-input synthesis---one prompt per parameter per variant under \texttt{tests\-per\-oper\-a\-tion=100}---while the soft-error rule cache contributes a one-time $\sim$2 prompts per distinct API. The remaining $\sim$8\,h covers scenario extraction, variant generation, JUnit emission, in-process execution, and trace-aware oracle evaluation. Table~\ref{tab:faults} shows detection on the most recent end-to-end run: all ten injected faults caught.

\section{Related Work}\label{sec:rw}

EvoMaster~\cite{Arcuri2017EvoMaster,Arcuri2019EvoMasterTOSEM} pioneered evolutionary search-based REST API test generation. RESTest~\cite{MartinLopez2021RESTest}, on which MIST builds, added constraint-based and ART generators. RESTler~\cite{Atlidakis2019RESTler} introduced stateful fuzzing; Morest~\cite{Liu2022MoRest} added execution feedback over a request graph; Schemathesis~\cite{HatfieldDodds2022Schemathesis} derives property-based fuzzers from the schema. A more recent line uses LLMs or reinforcement learning for input synthesis~\cite{Kim2023ARATRL,Corradini2024DeepREST,Kim2024RESTGPT,Kim2025LlamaRestTest,Stennett2025AutoRestTest}. All of the above target single-service APIs and rely on the HTTP status class as the primary oracle. Distributed tracing itself originates with Dapper~\cite{Sigelman2010Dapper} and is now standardised by OpenTelemetry~\cite{OpenTelemetry} and Jaeger~\cite{Jaeger}; the TrainTicket benchmark~\cite{Zhou2021TrainTicket} is the canonical microservice testbed. To our knowledge, MIST is the first openly available REST API testing tool that mines workflow scenarios from traces and treats span-level evidence as a primary oracle.

\section{Conclusion}\label{sec:concl}

MIST attacks two gaps that hurt REST testing on microservices: the weak status-class oracle and the state-fabrication burden of internal endpoints. The Sniper Mutator localises the cause of each variant, Root API Mode hides internal state behind the trace, and the Trace-Aware Oracle combines status, structure, and body-pattern signals into a single verdict. The TrainTicket case study, the 10-fault corpus, and the bundled deployment are reproducible from one properties file.
